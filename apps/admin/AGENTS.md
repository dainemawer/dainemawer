# Agent Guide — admin

App-specific conventions for `apps/admin` (admin.dainemawer.com: customers, quotes, invoices). Repo-wide conventions live in the [root AGENTS.md](../../AGENTS.md) — read that first. This section is hand-maintained — only the block below it is auto-managed by `next dev`.

## Running it

- `pnpm --filter admin dev` serves on port 3001. It first starts a real local Postgres 17 (the `embedded-postgres` binaries, data in `.data/postgres`), applies migrations and seeds it, then runs `next dev` against it (`db/local.mts`). Don't swap this for an in-process database such as PGlite: `next dev` runs the app in several processes, and they overwrote each other's files.
- `db:migrate` and `db:seed` are only for a remote database and need `DATABASE_URL` in the shell. `pnpm dev` ignores a `DATABASE_URL` in `.env.local` on purpose: `vercel env pull` writes the production one there.
- Without `RESEND_API_KEY`, emails (magic links included) are printed to the dev server log instead of sent. Sign in by opening the logged link.
- Copy `.env.example` to `.env.local`; only `BETTER_AUTH_SECRET` is required locally.
- `.data/` is disposable: delete it to start from an empty database.

## Conventions

- **Money is integer minor units** (`bigint`, cents) end to end; quantities are hundredths. All arithmetic goes through `lib/totals.ts`, which the editor (live totals), the Server Actions (stored totals) and the PDF share. Never compute totals anywhere else.
- **Quotes and invoices are one `documents` table** with a `kind`. Every page is shared in `components/document-pages.tsx`; the route files under `app/(app)/quotes` and `app/(app)/invoices` only pass their kind.
- **`expired` and `overdue` are derived** from dates on read (`displayStatus` in `lib/documents.ts`), never stored. `allowedActions` (buttons) and `statusTargets` (the Change status menu, applied by `setStatus`) are the one source of truth for which transitions a status permits; Server Actions re-check them.
- **Numbers are gapless per kind and year**: allocated by an upsert on `counters` inside the create transaction. That's why invoices are voided, never deleted.
- **Auth**: Better Auth with magic links, sign-up disabled, one user (`ADMIN_EMAIL`, created by `db:seed`). `proxy.ts` only checks for a session cookie. The real check is `requireSession()`, called by every data read in `lib/queries.ts` / `lib/dashboard.ts` (so no page can show data without a session, however it's laid out), every Server Action, and the PDF route handlers.
- **Rendering: Cache Components + Partial Prefetching** (`next.config.ts`). Every page is a sync component that renders its headings and buttons into the prerendered static shell, and streams its data behind `<Suspense>` with a fallback from `components/skeletons.tsx`. Never `await` params, searchParams or data at the top of a page or layout; push it into a child inside the boundary. The layout is static too (only the signed-in email streams).
- **Never put data in the static shell.** The shell is served to anyone who gets past `proxy.ts` (a made-up cookie does). That's why data only comes through the session-gated readers, and why there's no UI-level `"use cache"` on components that render data.
- **Caching**: the readers call unexported `"use cache: remote"` queries tagged per table (`lib/cache-tags.ts`, `cacheLife("hours")`). Writes expire tags: `updateTag` in Server Actions, `revalidateTag(tag, { expire: 0 })` in the cron route. A write that bypasses those (manual SQL, a script) shows up within the hour or on the next deploy. Anything derived from today's date takes `getToday()` (`lib/today.ts`, cached for minutes) as a value or cache-key argument, never `new Date()` while rendering; actions and the cron use `todayISO()`. `requireSession` is `"use cache: private"` (browser-only, 5-minute stale) so signed-in App Shells can be prefetched; the server still checks every request.
- `next dev` doesn't serve `use cache` hits the way production does. Check caching with `next build && next start` against the local database.
- **Recurring invoices** are schedules (`recurring_invoices` + `recurring_lines`) that a daily Vercel Cron (`vercel.json`, 04:00 UTC = 06:00 Cape Town) turns into **draft** invoices via `lib/recurring.ts`, then sends a list to review to Telegram. Nothing goes to a client automatically, and their invoices can never be emailed: the detail page swaps Send for Mark sent and `sendDocument` refuses any document with a `recurringId` (`allowedActions(…, { recurring })`). Dates live in `lib/recurring-dates.ts` (anchor day, month-end fallback, catch-up). Duplicates are impossible: the schedule row is locked while it issues, and `documents` has a unique index on `(recurring_id, recurring_date)`. Cron only runs on production deployments.
- **Expenses** (`lib/expenses/`, `/expenses`) analyse personal Investec accounts. **Transactions are never stored**: pages fetch them live from Investec (`investec.ts`, never cached, behind `connection()`). The database only holds what the app adds, keyed by Investec's transaction `uuid`: a label per transaction (category, deductible, source), rules and notes (the classifier's memory), and monthly totals per category (`expense_monthly`) so trends outlive Investec's ~180-day history. Labelling (`recon.ts`) runs rules first, then Claude through AI Gateway (`ai.ts`: Haiku classifies merchants, Sonnet proposes the category list once); without AI Gateway credentials it falls back to keyword matching (`offline.ts`). Labels are insert-only for the AI and rules, so a re-run never overwrites your own; monthly totals are always recomputed from Investec, never incremented, and only for months that start inside the history window. A daily cron (`/api/cron/expenses`) re-reads the whole history window, labels anything new and recomputes every month's totals (one request per account, so a missed run or a failed AI call heals itself), then sends a summary to Telegram. Totals group by posting date while Investec filters by purchase date, so month fetches start `POSTING_LAG_DAYS` early. Pure logic (merchant keys, rule matching, totals, trends) is in `transactions.ts` and tested. `.env.example` points local dev at Investec's public sandbox.
- Shared zod pieces live in `lib/validation.ts` and number allocation in `lib/numbering.ts`, not in the `"use server"` files: every export of those becomes a public Server Action.
- **Projects** (`/projects`) read Linear's GraphQL API (`lib/linear.ts`, `"use cache: remote"`, tag `projects`, hourly). A signed Linear webhook (`/api/webhooks/linear`, `LINEAR_WEBHOOK_SECRET`) expires the tag on any project or milestone change, and `issues` on any issue change. Without `LINEAR_API_KEY`, local dev shows `SAMPLE_PROJECTS` and production shows "Linear isn't connected".
- **Sign-in and security** (`lib/auth.ts`): a passkey is the main way in; magic links work until the first passkey is added, then only with `ALLOW_EMAIL_SIGN_IN=1` (the recovery path). Every new session is logged and sent to Telegram (Better Auth's `after` hook). `audit()` (`lib/audit.ts`) appends to `audit_events` and never throws; call it after any sensitive write (sends, settings, expense rules and accounts) with a short detail. Settings → Security lists passkeys, live sessions (with "Sign out other sessions") and the last 50 events. A failing cron calls `reportCronFailure()` (`lib/cron-auth.ts`), which logs it and sends it to Telegram.
- **Telegram** (`lib/telegram.ts`) is the only channel for notifications to you; email is for sign-in links and clients' documents. `sendTelegram()` posts to `TELEGRAM_CHAT_ID` only and never throws. Audit events go to Telegram per `AUDIT_TELEGRAM` in `lib/audit-actions.ts` ("alert" buzzes, "quiet" is silent); the expenses summary and new recurring drafts send their own quiet message. Without the token it logs instead.
- **Telegram assistant**: what you send the bot arrives at `app/api/webhooks/telegram` (checked against `TELEGRAM_WEBHOOK_SECRET` and your chat ID; registered with `pnpm --filter admin telegram:webhook <origin>`). `lib/assistant/` answers with Claude through the AI Gateway and read-only tools (`tools.ts`) over the normal data layer, which runs inside `asOwner()` (`lib/session.ts`) in place of a browser session. Never give a tool a write, and never call `asOwner()` from anything a request can reach without its own proof of identity. The last hour of conversation (`assistant_messages`, pruned after a day) gives follow-ups context; `/new` clears it.
- Server Actions that the client calls for errors return `{ error }` instead of throwing — thrown messages are redacted in production. Only a `UserError` (`lib/errors.ts`) reaches the page as written; anything else goes through `errorMessage()`, which logs it and shows the action's generic message.
- Schema changes: edit `db/schema.ts`, then `pnpm --filter admin db:generate` and commit the SQL in `db/migrations`. Vercel runs `db:migrate` before production builds only (`vercel.json`): previews share the production database, so a PR must never migrate it.
- **Layout**: every page header (`components/page-header.tsx`) shows a breadcrumb trail from Dashboard: pass `breadcrumbs` (the pages above) and `current` when the title isn't plain text; the dashboard passes `breadcrumbs={false}`, as do Expenses pages, whose layout shows one trail above its tabs. Only the dashboard fills the screen, via its `[data-wide]` block (a direct child of `<main>`) and the `dashboard` CSS variant, which ignores pages Next keeps hidden in the DOM. Don't key layout off the route with `useSelectedLayoutSegment` in the layout: on `[id]` routes it needs a Suspense boundary around the whole shell. Collapsing the sidebar animates the grid columns and the shell's width.
- **Dashboard HUD** (`components/hud/`): the clock and weather band above the money. Both are client components in the static shell, outside the data's `<Suspense>`: the clock only renders in the browser (`useSyncExternalStore` with a null server snapshot, so no `new Date()` during prerender), and always shows Cape Town time (`lib/hud.ts`). Weather asks for the browser's location (hence `geolocation=(self)` in the Permissions-Policy), falls back to Cape Town, and fetches `/api/weather`, which rounds coordinates to ~1 km and calls Open-Meteo (forecast) and Nominatim (place name) server-side, cached remotely, so the CSP keeps `connect-src 'self'`. Pure parts (`lib/hud.ts`, `lib/weather.ts`) are tested.
- **HUD calendar** (`lib/calendar.ts`, `lib/calendar-feeds.ts`, `components/hud/calendar.tsx`): today and tomorrow from `CALENDAR_WORK_URL` and `CALENDAR_PERSONAL_URL` (Google "secret address in iCal format" feeds; the URL is the secret, never log it). Each feed is fetched and cut down to the two days inside a `"use cache: remote"` entry (10-minute revalidate), keyed by `getToday()`, so only the short list is stored. It's data, so it renders behind `requireSession()` in its own `<Suspense>`; `agenda-view.tsx` adds now/next and free time (08:00–18:00, `WORKDAY` in `lib/agenda.ts`) in the browser. Parsing uses ical.js with two deliberate workarounds, explained at the top of `lib/calendar.ts`: exceptions are grouped by UID and passed to `ICAL.Event` (its default relates every exception in the file to every series, which ran a 17 MB feed out of memory), and times convert with Intl from the TZID rather than ical.js's VTIMEZONE engine. Cancelled events and ones the feed's owner declined are left out.
- **HUD exchange rates** (`lib/fx.ts`, `lib/fx-rates.ts`, `components/hud/fx.tsx`): rand per USD, EUR and GBP from the ECB's daily reference rates via Frankfurter (no key), a month of history for the sparklines, cached in the shared runtime cache for hours and keyed by Cape Town's date.
- **HUD Linear** (`lib/linear-today.ts`, `getLinearToday()` in `lib/linear.ts`, `components/hud/linear.tsx`): the API key's own assigned issues that are in progress, to do, due by today or done since midnight, sorted into overdue, due today, in progress, then urgent and high to-dos (backlog only when due). Cached for minutes under tag `issues`.
- **Income in rand** (`/income`, `lib/income.ts`, `lib/income-report.ts`): paid invoices valued at the ECB rate (Frankfurter, base EUR, crossed to rand) on the paid date or the last working day before it, by SA tax year (March–February). Computed on read, not stored: past ECB rates never change. The only place currencies are added together; the dashboard shows this month, this tax year and last.
- **Health** (`lib/health.ts`, `health_days`): a slow cut (`PLAN`: 88 → 85 kg at 0.5 kg a week, from 2 Nov 2026) tracked without calories. One row per Cape Town day: readings (weight in grams, steps, sleep minutes, resting heart rate) and ticks (protein meals, kitchen closed, worked out). Readings arrive from an Apple Health Shortcut at `/api/webhooks/health` (bearer `HEALTH_INGEST_SECRET`; Garmin syncs into Apple Health, so one route covers both). A day can be sent again: each send overwrites only the readings it carries (`coalesce`), and numbers may be locale text ("88,2"). Weight is shown as a smoothed trend (`weightTrend`, Hacker's Diet smoothing 0.1), never the raw scale; the rate is the trend's change over seven days. Pure logic is tested in `tests/health.test.ts`.
- **Sidebar**: pages and groups are listed once in `components/app-nav.tsx`. Collapsing to icons is CSS keyed off `<html data-sidebar="collapsed">` (the `sidebar-collapsed` / `sidebar-expanded` variants in `globals.css`), set by `components/sidebar-toggle.tsx` and restored before first paint by the inline script in `app/layout.tsx`, so the layout stays a static shell. Collapsed, every page is its own icon; groups only exist expanded.
- **Emails**: anything with an HTML version lives in `lib/emails/` as tables and inline styles, always with a plain-text `text` too. Images come from `public/email/`, which `proxy.ts` serves without a session; reference them by the absolute origin of the link in the email.
- UI is shadcn/ui (`components/ui`, added with the shadcn CLI) themed onto the blog's tokens in `app/globals.css`. Use the semantic classes (`text-muted-foreground`, `bg-muted`); `--color-muted` means a background here, unlike in the blog.
